# KV Cache 友好的上下文布局

## R — 原文

> "1.系统提示词和工具定义一旦确定就不要改……2.动态信息永远追加到末尾……3.使用标准 API 格式,不要自行拼接消息。" —— 第 2 章 2.3(三条核心结论)

> "若 token 序列从某个位置开始不同,首个不同 token 及其后的 KV 状态需要重新计算;此前位置的 KV 状态不受这次改动影响。" —— 第 2 章 2.3

## I — 阐释

推理引擎缓存前文的中间计算结果(KV Cache),前缀字节级不变才能复用;改动越靠前,重算越多。这把缓存从"性能优化"变成"架构约束":提示词的物理排列首先由缓存经济性决定。三条纪律: 静态前缀(系统提示词+核心工具定义)保持字节稳定,任何动态内容(时间戳/用户状态/新工具 schema)一律追加到上下文末尾而不是回写前缀;必须用标准消息角色,自行拼接字符串会偏离训练格式、破坏思维链保留。延伸决策: N 个二值动态条件若放前缀会产生 2^N 种缓存键,必须后置;子 Agent 继承父上下文时逐字节对齐可命中跨请求 Prompt Cache;按需加载的工具 schema 追加到轨迹末尾即成为"只增不改"的历史,不破坏缓存。

## A1 — 书中案例

reported_case(第 2 章 2.3 开篇): 客服 Agent 每天处理 10 万次对话,工程师在系统提示词加一行 `Current time: {{now}}` 实时时间戳,次日全部对话首 token 延迟从 0.5 秒涨到 3-5 秒,月度推理账单几乎翻倍。另: Claude Code(2.3.4)把系统提示词用缓存边界分为"跨用户全局缓存段"与"会话特定段",子 Agent 与父 Agent 字节级对齐,工具结果替换字符串首次出现即冻结。

## A2 — 触发场景

- 发现 API 账单/首字延迟异常增长,问"为什么改了一行提示词变这么慢"
- 设计上下文结构: 时间/余额/环境状态要注入哪里;工具要不要全量放前缀
- 评审: 动态排序工具列表、每轮重写 system、滑动窗口砍历史
- 语言信号: "KV Cache", "prompt cache", "前缀缓存", "首 token 延迟", "TTFT 变慢", "cache hit"
- 区分: 上下文太长要压缩见 context-compression(压缩与缓存互补:批量压 tool results、别每轮压);本卡管布局不变性

## E — 执行步骤

1. 盘点上下文内容,分两类: 静态(系统提示词、核心工具定义、固定 few-shot 示例集)与动态(时间、用户状态、状态栏、运行中发现的工具)。完成标准: 每项内容有归属标签。
2. 固定静态前缀: 一次写定后字节冻结;每类任务用固定示例集,不逐请求挑选"最相关"示例。完成标准: 连续两次请求的前缀 diff 为空。
3. 动态信息全部改为末尾追加: 时间戳、额度等作为 user 消息或状态栏注入末尾;需要时也可改为工具按需获取。完成标准: 无任何动态内容位于前缀。
4. 工具集管理: 核心常驻工具进前缀;长尾工具走按需发现,schema 首次加载后追加到轨迹原位置、后续不搬运(见 tool-design-discovery)。
5. 验证: 对同一会话连续发起请求,记录缓存命中 token 数与 TTFT;再故意改动前缀一个字符对照,确认命中下降即机制生效。

输入契约: 完整上下文内容清单、服务商缓存计费方式(各家的启用/计费差异需查最新文档)。输出契约: 布局方案(前缀清单/动态注入点)+缓存命中率对照记录。

## B — 边界

- 不适用于: 无状态单轮调用、前缀本就极短(<数百 token)的场景,收益有限
- 原书警告: 缓存读取非零成本(约为首次计算 1/10);Skills/状态栏"对缓存友好"≠零成本,首次加载仍要付一次计算
- KV Cache 省的是历史 K/V 重算,但每个新 token 的注意力仍遍历全部缓存,长上下文解码仍线性变慢——布局优化不解决"太长"本身
- "可编辑 KV Cache"研究(2.3.5)属前沿,生产默认仍守三条结论
- 与压缩冲突点: 压缩历史会缩短可命中前缀,二者收益不可加和(见 model-selection-cost 的实测原则)
