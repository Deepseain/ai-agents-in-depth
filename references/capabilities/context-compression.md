# 上下文压缩策略设计

## R — 原文

> "压缩不是在单次 API 调用的过程中修改上下文,而是在两次 API 调用之间,由 Agent 框架对消息列表进行预处理……最好在上下文接近阈值时批量压缩,而不是每轮都压。" —— 第 2 章 2.7.3

> "隔离则让噪声从一开始就与主上下文绝缘……代价是子 Agent 看不到主 Agent 的完整上下文,任务描述必须自包含、目标明确。" —— 第 2 章 2.7.6

## I — 阐释

压缩有三个动机: 控制长度与成本;提升思考质量(总结后的知识比散落的原始记录更易用——注意力能检索,不擅长归纳);缓解上下文焦虑(模型以为窗口快满会提前草率收尾)。设计上区分四原则: 信息价值非均匀(决策>证据>噪声,对噪声直接删、做摘要反而浪费)、语义完整性("Sutskever 于 2024 年 5 月离开 OpenAI"不能压成"离开")、任务相关性(检索类保广度/分析类保深度/创作类保灵感点,按当前查询意图压缩)、压缩即理解(压缩模块能力要接近主模型)。与 KV Cache 的配合: 静态前缀永不压,只压轨迹中的 tool results;批量压不每轮压(频繁压缩=频繁击穿缓存)。生产形态是分层: 工具结果预算控制(大输出落盘留预览)→噪声直删→API 层微压缩→归档式摘要(git log 式逐轮)→全量压缩兜底(带连续失败熔断)。更釜底抽薪的是隔离: 大体积中间内容委派子 Agent,只回传结论摘要。

## A1 — 书中案例

worked_example(第 2 章 实验 2-10): 追踪 OpenAI 联创职业状态,7 次搜索累计 36.7 万字符。无压缩:第 5 轮超 128K 窗口失败;个体摘要(压缩率 10.9%)12 次迭代 27.6 万 token;上下文感知压缩(压缩提示带查询意图与已知信息,3.0%)7 次迭代 4 万 token,曾把 150K 字符压到 2K 仍保留姓名与职位变动;自适应窗口化(80% 阈值触发+[COMPRESSED] 防重复标记)保初期完整信息。整体 token -75%+。

## A2 — 触发场景

- 长任务上下文逼近窗口、成本失控,或模型开始"找不到"明明看过的信息(上下文腐化)
- 工具返回巨大(网页/日志/搜索结果)撑爆预算
- 要决定"什么时候压、压什么、谁来做压缩"
- 语言信号: "上下文压缩", "context compression", "context rot", "上下文腐化", "摘要历史", "窗口不够用"
- 区分: 状态显式化见 agent-status-bar(状态栏是压缩的一种,但本卡管大体积历史);子 Agent 隔离属实现手段之一,完整协作设计见 multi-agent-architecture;跨会话知识见 user-memory-system

## E — 执行步骤

1. 定触发: 监控上下文使用率,超过窗口约 80% 才激活压缩(阈值触发),不每轮压。完成标准: 有使用率监控与触发阈值。
2. 定压缩对象与保真清单: 静态前缀永不压;只压轨迹中已远离焦点的 tool results;必须保留四类信息——关键决策、约束与理由、失败路径、来源引用。噪声(导航栏/页脚)直接删不做摘要。完成标准: 四类保留项逐类可检查。
3. 写压缩提示: 包含当前查询意图(`Given the search query: {query}`)与已积累结论(`Current context: ...`),要求结构化输出;压缩模块用接近主模型能力的模型。完成标准: 压缩结果含任务后续需要的关键实体/数值/时间。
4. 分层实施(生产): 大工具输出落盘只留摘要预览(替换字符串冻结保缓存一致)→噪声直删→归档式逐轮摘要→全量压缩兜底,并为连续压缩失败配熔断(连续 3 次失败即放弃压缩转其他策略,阈值来自 Claude Code 生产统计)。
5. 优先考虑隔离: 对"大范围搜索/探索"类子任务改派子 Agent,主上下文只接收结论摘要;任务描述须自包含。
6. 验证: 同一任务对比压缩前后 token 总量、任务成功率、关键信息抽查(压缩后模型能否仍答出早前细节);压缩与缓存同开时完整任务实测收益(不可加和)。

输入契约: 上下文预算、任务类型(检索/分析/创作)、可用的压缩模型。输出契约: 压缩策略配置(阈值/对象/保留清单/提示模板)+前后对照数据。

## B — 边界

- 极端压缩有不可逆信息损失风险(150K→2K)——带引用的压缩(保留源链接可回溯)或落盘原始数据是缓解手段
- 压缩会缩短可命中缓存的前缀,与缓存优化收益不可加和,必须完整任务实测(原书实测: 单开缓存 -28.3%、单开压缩 -17.5%、同开 -30%)
- "上下文学习本质是检索"是作者引述研究的解释性论断,作为设计依据而非已证事实
- 别把压缩当唯一手段: 隔离优于压缩;定期把进展文档化(写文件)比把一切留在轨迹里可靠
- 开放任务中"该保留什么"判断失败率非零,熔断器是必要配件而非可选优化
