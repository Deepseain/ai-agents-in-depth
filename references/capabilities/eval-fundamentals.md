# 评估体系基础:任务定义、指标口径与数据集设计

## R — 原文

> "Pass@k = 1-(1-p)^k……Pass^k = p^k。前一个数字适合衡量探索时的能力天花板,后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。" —— 第 7 章 7.2

> "Agent 很容易写一篇洋洋洒洒的报告,说任务已经全部完成……评估框架必须核实机器可独立复核的事实,而非 Agent 的自我陈述。" —— 第 7 章 7.4.2

## I — 阐释

评估体系四环节: 什么算成功(指标)、任务从何而来(数据集)、由谁验证(环境)、分数如何变决策(后两张卡)。①任务定义四组成部分: 给 Agent 的工单、给用户模拟器的行为规范(关键设计: known_info 显式建模用户认知边界,用户不知的信息 Agent 只能提问获取;验收口径精确到"仅测速 excellent 算解决";事实锚定要求回答基于工具结果——缺它模拟用户会被 Agent 忽悠,评估退化为两模型互相确认)、可重置的初始状态、四层评分标准(动作/终态断言/信息告知/自然语言断言,按 reward_basis 聚合)。②指标口径: Pass@k 是能力上限(技术奇观),Pass^k(连续 k 次全对)是业务可靠性——单次 0.6 时 Pass@5≈99% 但 Pass^5≈7.8%;带副作用的任务在沙盒采样,每次失败都计入可靠性。③环境五要素: 数据集/可重置状态/原子工具(抽象过高会让评估退化)/评分标准/执行协议;人机交互型(测沟通策略)与工具调用型(测状态变更)两类。④数据集: 验证器要双重验证(FAIL_TO_PASS 证明修了+PASS_TO_PASS 证明没弄坏)、难度分层具诊断价值、防泄漏(组合信息源/参数化模板/金丝雀)、三来源(公开基准粗筛+自建业务集决策+生产轨迹回流,成本最高准确性也最高)。

## A1 — 书中案例

worked_example(第 7 章 7.1): τ²-bench telecom 任务 "[mobile_data_issue]airplane_mode_on|roaming_off"——故障一半在用户侧(飞行模式/漫游开关)、一半在运营商侧,Agent 查数据库只见"配置正常",只有引导用户查状态栏才能发现;该设计靠 known_info 边界+双控环境(用户也有工具)实现。失败轨迹同样有教学价值: Agent 选错线路,工具返回明确显示号码不符却不修正,消耗数十条消息后转人工——二元奖励只给 0 分,不说明错在哪(这正是要配失败归因的原因)。reported_case(7.4.5): SWE-bench Verified 发布前 93 名 Python 开发者逐条审查 2294 任务仅留 500(淘汰 71%),信噪比升高且评估成本降约 80%。

## A2 — 触发场景

- 团队要判断"Agent 变好了还是变差了",从零搭评估集
- 引用公开基准分数做产品决策;或自建任务不知怎么写验证器
- 定义"成功"时纠结单次成功率、重试后成功率、连续成功率
- 语言信号: "评估 agent", "benchmark 设计", "Pass@k", "用户模拟器", "验证器", "评估数据集", "tau-bench 类环境"
- 区分: 打分之后的失败定位见 llm-judge-failure-attribution;分数如何驱动选型与迭代见 model-selection-cost 与 eval-driven-iteration;本卡管"评估的构造学"

## E — 执行步骤

1. 定指标口径: 按业务风险选——探索/科研类报 Pass@k 或 Best@k;支付/退款/生产类报 Pass^k;报告写清 k 的含义(同任务独立采样 vs 连续任务),失败计入指标不重试覆盖。完成标准: 口径选择有业务理由。
2. 写任务四组成部分(每条任务): ①工单(用户初始表述,故意不完整);②用户模拟器规范(known_info 划认知边界/情绪与耐心设定/验收口径精确化/事实锚定: 回答必须基于工具结果);③initial_state 重置动作(两侧状态回到同一起点);④评分标准(终态断言优先,必要信息告知用 communicate_info 检查,关键动作检查)。完成标准: 不看 Agent 轨迹也能判定对错。
3. 搭环境五要素: 可重置状态(业务逻辑真实)、原子工具(无"解决问题"级高层抽象)、评分标准、执行协议(终止信号/轮数上限/耐心耗尽计失败)。参照 Verifiers 分层选型(单轮/工具型/有状态/沙盒)。
4. 设计数据集: 难度分三级(失败层级具诊断价值: 基础工具→多步规划→复杂组合);防泄漏(组合多信息源、参数化模板生成无限实例、嵌入金丝雀 GUID);质量控制(发布前逐条人审,淘汰率宁高勿低;长期维护修环境/描述/验证/初始状态四类问题)。三来源配比: 起步=公开基准+手写业务集,上线后生产轨迹回流(用户纠正/点踩/事后审计发现的问题案例)沉淀回归用例。
5. 验证: 人肉执行抽样任务(每难度各一)——回答两个问题: 任务描述是否存在多种合理解释?蒙混过关成本最低的路径是什么、验证器能否拦住?

输入契约: 被评 Agent 的任务分布、业务风险等级、可用仿真能力(用户模拟器/环境状态)。输出契约: 评估集(任务文件+验证器)+指标口径说明+人肉抽检记录。

## B — 边界

- 公开基准分数不直接指导产品决策(GAIA +2pp 与退款成功率无必然关系),迁移的是设计手法
- 二元奖励以过程颗粒度换跨模型可比性——生产评估还需失败归因补充"错在哪"
- 模拟用户本身是 LLM,可能系统性低估边缘场景(情绪激动/表达不清的用户),其质量也需验证
- 带副作用任务不得"重试直到成功": 在沙盒/可回滚环境采样
- 验证器过松会放过表面完成,过严会把对的判错——OSWorld 15 个月暴露 300+ 问题说明维护是常态不是例外
