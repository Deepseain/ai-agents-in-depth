# 异步事件驱动的 Agent 设计

## R — 原文

> "所有的输入、输出、思考过程和外部交互都被统一建模为事件流……取消式处理用于紧急事件,其本质是为紧急事件提前制造一个安全点。" —— 第 6 章 6.2.1/6.2.6

> "为未完成的工具生成占位符响应……追加打断事件,重新调用 LLM。从 LLM 的视角看,assistant message 仍然有配对的 tool result。" —— 第 6 章 6.2.7(兼容规则 3)

## I — 阐释

同步 Agent 假设"世界等它想完",真实助手必须响应随时到达的外部事件。架构骨架是事件循环: 每轮从输入队列取若干事件追加到轨迹、调一次 LLM、执行其决定的工具、回到等待。前提性工作是把每个输入建模为结构化事件(来源: 用户/联系人/系统;渠道;内容含紧急度与是否需回复;上下文: 关联哪个对话线程)——这也是防注入的基础(分清用户输入与工具结果)。处理策略按紧急度三选: 紧急事件(用户中断/监督指令)用取消式——主动中断当前步骤制造安全点,未完成工具以显式占位符收尾(不伪造成功);常规事件(工具结果/用户补充)队列式——等安全点批量追加,配状态栏标记"[未处理事件 i/N]"+末尾汇总防只回应最后一个;独立轻查询(问天气)并行式——另起会话快速应答,标记"与主任务并行"。同步接口的兼容五规则核心: 打断时用占位符修复 tool 配对、取消生成时不回灌半截输出。工具设计上把"启动"与"完成"解耦(initiate_phone_call 立即返回任务 ID,进展走事件)。

## A1 — 书中案例

firsthand(第 6 章 6.2.2): PineClaw——OpenClaw 的 Cron/Heartbeat 是时间驱动,电话进行中客服要求 OTP 验证时,轮询式通知来不及(客服挂断、任务失败);在 Gateway 与 Pine API 之间建实时 Channel 后关键事件即时推送 Agent。worked_example(实验 6-2 验证场景): 三个脚本并行跑(每秒 3%/2%/1%),最快者完成后 Agent 查询其余进度、取消未过 50% 的那个——验证任务句柄、状态查询与级联取消。

## A2 — 触发场景

- Agent 要接收邮件/IM/定时器/webhook 等外部触发,或"活人感"地异步沟通
- 用户要在 Agent 执行中插话/打断/补充要求
- 工具长时间后台运行,Agent 该等还是该先干别的
- 语言信号: "事件驱动", "event-driven", "异步 agent", "打断", "interrupt", "轮询 vs 推送", "消息队列"
- 区分: 用户触达与多渠道召回、虚拟身份属配套设施(见原文 6.2.4-6.2.5,通用原则: 消息即工具、独立身份+隔离环境);多 Agent 的控制平面见 multi-agent-architecture(本卡管单 Agent 实例内的事件处理)

## E — 执行步骤

1. 统一事件源: 定时器(set_timer 一次性/循环)、后台任务监控(monitor 新增输出或关键词)、外部通道(webhook/新邮件)全部注册进一个事件队列。完成标准: 每类来源有触发条件与过滤规则,事件载荷含足够上下文(减少唤醒后补查)。
2. 结构化建模: 每个事件带来源/渠道/内容(含紧急度、需否回复)/上下文(关联线程)。完成标准: 第三方消息不会被误当用户指令(来源字段可判)。
3. 实现三种策略: 紧急(用户中断、监督指令、高优外部触发)→取消当前推理/发取消信号给工具、清空队列、连紧急事件一起追加轨迹、立即重调 LLM;常规→入队,在工具返回的安全点一次性批量追加;独立轻查询→并行会话即时回答并标记与主任务并行。
4. 同步接口兼容: 及时记录已完成消息;工具完成才记结果;打断时为未完成工具生成占位符("工具正在后台执行,请优先处理新事件")保证配对;无原生续接接口时取消生成、保留已确认消息后重请求,不回灌半截输出;非打断事件一律排队。
5. 工具语义异步化: 长耗时操作命名与描述传达"发起即返回"(initiate_*),返回任务 ID+初始状态,结果作为后续事件到达;占位符须防"已启动"被当"已完成"——靠任务状态字段与结果校验。
6. 防注意力分散: 批量事件逐条加序号标记,末尾加汇总("共 4 个未处理事件……请确保回应涵盖所有信息")。
7. 验证: 三场景实测——执行中打断(占位符配对、原任务恢复)、批量补充(全部事件被消费)、并行查询(主任务不中断);原生异步模型(如支持中途引导的)另测结果归属与多更新综合使用。

输入契约: 事件源清单与紧急度规则、模型是否支持原生异步(决定走兼容层还是原生协议)。输出契约: 事件结构定义+三策略实现+打断/批量/并行测试记录。

## B — 边界

- 用了 asyncio ≠ 模型有原生异步能力——先查模型/API 的消息时序支持
- 硬编码紧急度规则有局限,事件的语义决定处理方式——建议轻量分类 LLM 做事件路由器
- 取消点必须是能安全收尾的位置;未完成的工具结果用显式占位符,不能伪造成功
- 批量处理的固有风险: 模型只盯最后一个事件——序号标记+汇总是缓解,原生异步也仍需检查"是否综合使用了所有更新"
- 接到"停止"消息不等于已撤销已发生的动作;工具须响应取消信号
