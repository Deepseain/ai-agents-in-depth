# 流程驱动的系统提示词与工具定义设计

## R — 原文

> "流程驱动的提示词就像一份优秀的新员工培训手册,提供了清晰的标准操作流程(SOP)……当遇到异常时,模型可以根据当前所处的阶段确定处理方式,而不是遍历所有规则去寻找匹配项。" —— 第 2 章 2.4.3

> "大语言模型的优势在于遵循复杂指令……但不应该在业务规则制定上被赋予过多的自由裁量权。" —— 第 2 章 2.4.4

## I — 阐释

系统提示词是 Agent 的"岗位说明书",设计分四个正交维度: 语气(简洁、大写保留给关键约束)、格式(XML 标签承载机器可解析语义 + Markdown 承载人读层次)、组织方式(流程驱动 SOP 优先于规则堆砌——模型任何时刻都知道自己在哪个阶段、异常按阶段处理)、内容(业务规则必须细化到可执行,而非"视情况选择")。判据是"聪明的新员工读完会不会做"。业务规则细化是产品经理的职责: 模糊口径("根据任务情况")导致行为不可预测,要把计费方式、成功率映射、金额粒度写死,并明确写出禁止项(如 NEVER 用百分比计费于退款)。工具定义与提示词同为静态前缀: 描述要写"何时用"而非"能做什么"、明确边界反例、参数用具体示例、注明执行代价,附 1-5 个调用示例。

## A1 — 书中案例

worked_example(第 2 章 2.4.4): Pine 类电话砍价 Agent 的计费规则——三种计费模式(按省钱提成/固定小费/困难任务预收款)若留模糊,同一任务在不同时间得到不同分类;细化后明确"提成仅限谈判降低现有账单,退款和取消服务绝对用固定费"、成功率映射(>60% 可退款、<30% 拒接)、金额粒度写死(每分钟 $0.05,四舍五入到整数美元)。消融证据(实验 2-4): 打乱信息组织致成功率降 30%+,移除工具描述文本致调用错误率 +45%。

## A2 — 触发场景

- 从零写系统提示词,或现有提示词越堆越长、模型行为不稳定
- 模型总在同类场景违规(跳过身份验证、计费口径漂移、忘记先查后改)
- 工具调用频繁出错,想改模型前先检查描述
- 语言信号: "system prompt 怎么写", "提示词设计", "业务规则写进提示词", "工具描述 description", "为什么 Agent 不遵守规则"
- 区分: 防外部恶意内容劫持见 prompt-injection-defense(本卡防的是设计不当);规则多到提示词装不下时见 skill-authoring(渐进式披露)

## E — 执行步骤

1. 定身份与语气: 一段角色定义 + 输出长度约束(如"无法完成时控制在 1-2 句")。完成标准: 聪明新员工读完知道自己是谁、对谁说话。
2. 写流程 SOP: 按执行顺序列阶段(如: 验证身份→查询订单→核对政策→执行→确认告知),每阶段含目标与异常处理;规则只在对应阶段出现。完成标准: 无游离于流程外的散规则。
3. 细化业务规则: 逐条把模糊口径改写为可执行判定(触发条件→动作→例外→验证方式);高风险规则用大写 NEVER/必须显式禁止。完成标准: 两人读同一条规则会做同一件事;剩余模糊项列清单交产品确认,不静默猜。
4. 结构化: XML 标签包语义块(如 <refund_policy>),Markdown 标题分层;few-shot 示例按任务类固定成组(2-3 个覆盖边界,不逐请求挑选)。
5. 写工具定义: 每个 description 含何时用/边界反例/参数具体示例(如 +8613888888888)/返回值结构/执行代价;附 1-5 个真实调用示例。
6. 验证: 在自己的任务集上对照测试;信息组织改动做消融(保持内容只打乱结构看是否掉分)。

输入契约: Agent 的业务目标、完整业务规则清单、可用工具列表。缺失处理: 规则含糊时列出待产品决策的问题,不替业务拍板。输出契约: 结构化提示词文档 + 工具定义清单 + 验证记录。

## B — 边界

- 不适用于纯闲聊/单轮问答——无需 SOP 的场景堆流程反而僵化
- 原书警告: 语气风格对成功率影响有限,别在措辞上过度投入;大写强调过度使用会稀释
- 提示词是静态前缀,动态状态别写进来(见 kv-cache-context-layout);规则膨胀到不可维护时升级为 Skills 而非继续堆
- 作者立场盲点: 该方法论源自高风险客服场景,对低风险快速原型可裁剪流程深度
- 提示词解决不了模型能力不足——改提示无效时应测模型替换(见 eval-driven-iteration)
