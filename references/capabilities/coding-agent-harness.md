# Coding Agent 流程与故障恢复

## R — 原文

> "Coding Agent 之所以成熟度高,不是因为代码生成模型特别强,而是因为软件工程几十年攒下的基础设施——测试套件、类型系统、版本控制——天然构成了一套强大的 Harness。" —— 第 5 章 5.3

> "错误处理的边界不是单次请求,而是整个恢复循环。在确认无法恢复之前,中间错误不应暴露给消费者。" —— 第 5 章 5.1.5

## I — 阐释

七核心工具(代码解释器/bash/读/写/编辑/glob/grep)即可支撑 Coding Agent。工作流: 先文档化(缺失则 Agent 主动生成架构概览;项目指令文件 CLAUDE.md/AGENTS.md 是面向 Agent 的行为约定与最经济稳定前缀)→复杂需求先澄清再设计文档(供人类审查的介入点)→实现后立即测试(把"测试通过"而非"代码写完"定义为完成)→自审(lint/审查子 Agent)→架构变更同步文档。判断任务是否适合 Agent 用四象限(目标明确×可自动验证);Harness 四组件: 验收基线(测试/CI)、执行边界(权限)、反馈信号(linter/类型/测试)、回退手段(Git/沙盒/快照)。可靠性来自故障工程: 四层故障(API/工具/上下文/控制流)→检测(先分类可重试与否,再用重复调用指纹与连续失败计数识别无进展循环,流式连接配空闲看门狗)→分级恢复(静默重试: 指数退避+抖动、区分前后台;降级接续: 提升上限/断点续写/换备用模型;才暴露给用户)→接管(轨迹存中立格式,思考拆可移植文字与不可移植凭证)→每条恢复路径配熔断(阈值来自生产数据)+死亡螺旋防护(错误路径禁调 LLM、递归深度计数)。

## A1 — 书中案例

reported_case(第 5 章 5.1.5): Claude Code 压缩熔断"连续 3 次"的阈值来自生产统计——曾有会话在压缩路径连续失败 3000 余次,仅此一类无效重试每天造成约 25 万次 API 调用浪费;真实死亡螺旋: 上下文溢出→停止钩子调 LLM 写 commit message→再溢出→再触发钩子。另(5.1.9): 忠诚度实验中替用户砍价的 Agent 一端泄密(抖出底价 12000)、一端过度拒绝,跷跷板效应——落成忠诚度守则(不泄露私密信息及其存在、拒绝时不念清单、私底底线≠对外立场、只执行明确指令、顶住重复施压)。

## A2 — 触发场景

- 构建/评估一个能改代码跑测试的 Agent(包括通用 Agent 的 coding 子系统)
- Agent"没跑测试就说完成"、卡死循环、API 限流雪崩、半截输出
- 决定某开发任务该不该交给 Agent(四象限判断)
- 语言信号: "coding agent", "测试驱动完成标准", "故障恢复", "熔断", "重试策略", "上下文溢出", "轨迹接管", "harness 设计"
- 区分: 通用工具安全栈见 execution-tool-safety;多 Agent 审查见 multi-agent-architecture(自审不可靠,审查须引新信息);搜索/编辑工具选型属实现细节(五编辑方案: old/new string 主流,首尾匹配兼顾大段删除)

## E — 执行步骤

1. 备齐 Harness 四组件: 验收基线(测试套件+CI)/执行边界(工作区限定、禁改目录)/反馈信号(lint+类型检查自动接入)/回退(Git 分支+快照)。完成标准: 任一改动可一键回滚,任一错误有结构化反馈。
2. 定完成标准: "测试通过"而非"代码写完"——验证由模型写不了的测试判定,完成声明须附带真实执行过的命令输出。
3. 实现故障分类与检测: 错误先分可重试(限流/过载/网络)与不可重试(参数非法/权限/工具不存在,须改输入不重试);对"工具名+参数"算指纹,相同指纹反复出现即无进展信号;每条恢复路径独立计数;流式配空闲看门狗。
4. 分级恢复: 静默重试(指数退避+随机抖动,尊重服务端等待提示;后台辅助调用失败直接放弃)→降级接续(输出触顶先提上限、再断点续写;主模型过载降级备用,先剥离私有格式块)→用尽才向用户暴露错误并附已尝试的手段。
5. 熔断与螺旋防护: 每条路径设连续失败上限(从生产统计取,如压缩 3 次);错误路径上禁用一切会再调 LLM 的副作用逻辑;递归深度计数器;全局上限(最大迭代/预算/连续失败转人工)。
6. 接管准备: 轨迹保存为中立格式——思考拆"可移植文字+凭证"两部分,工具调用只记名称与参数;跨厂商切换时凭证一律丢弃、文字以普通内容带入,严格端把历史调用改写为文字叙述。
7. 实现技巧: 并行工具调用+流式执行(首调用参数完整即执行)、读文件带行号、持久终端会话、写后即时 lint、环境信息(目录/分支/最近提交)走状态栏注入。
8. 验证: 注入四层故障(429 连发/工具反复报错/超长输出截断/触发停止钩子)各测一次,检查检测信号、恢复路径、熔断触发与用户可见性。

输入契约: 目标代码库与测试基础设施、可接受的自主权限边界、模型可用性(含备用模型)。输出契约: Harness 配置+故障处理映射表+故障注入测试记录。

## B — 边界

- 约束优先于指导: 能用代码强制的(linter/CI/类型)不写在提示词里;防"过程性错误"(删库重建也算"修复")要对动作设检查而非只看结果指标
- 故障只在同一批并行调用内传播: 一个读文件失败不取消兄弟调用、不中止任务
- "本地执行"不等于不安全,也不等于安全——权限取决于宿主沙盒与审批策略
- 自审不可靠: 单模型审查自己的输出,准确率反降(Huang et al.);审查必须引入新信息(测试执行/渲染/独立模型)
- 接管前查目标厂商凭证策略: "把思考删干净"在严格端反而通不过
- 作者场景为高可靠生产;个人脚本场景可裁剪熔断与接管深度,但完成标准与回退手段不可省
