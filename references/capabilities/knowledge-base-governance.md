# 知识库更新与治理:PR 审核流、定期整理与权限

## R — 原文

> "最稳妥的工程答案是:把知识库当成代码库,把每次知识变更当成一个 Pull Request……生产环境不应让任何一个模型绕过审核,直接改主分支或线上向量库。" —— 第 3 章 3.3.3.1

> "增量更新的优点是及时,但它每次只看到一个局部……系统还需要定期进行一次全量整理。" —— 第 3 章 3.3.3.2

## I — 阐释

知识库的正确性不在检索而在写入。两条更新路径并行: ①增量更新走 PR 流——Proposer Agent 从原始证据发现新事实/冲突/过期内容,在工作分支提最小且完整的 diff(检索相关已有知识后增删改,同步维护链接/索引/时间/证据引用);Reviewer Agent 独立拿变更前知识+diff+原始证据逐条核对,拒绝时给出指向具体证据和行号的可执行意见;迭代收敛后 CI 检格式/链接/元数据,通过才重建索引。两个 Agent 优先异源(不同家族相近能力),权限强制分工(Proposer 只写分支,Reviewer 只读)。②定期整理防"局部正确累积成全局混乱": 去重合并、回原始数据核查(不能只在摘要间相互改写,否则早期误读代代相传)、冲突做场景限定而非保留最新。三层数据分离: 只增不改的原始证据层、可持续修订的知识层、可重建的索引服务层。检索侧权限下推: 按调用者权限过滤,越权内容不得进入上下文;失效内容带版本/时间元数据在检索期过滤。

## A1 — 书中案例

worked_example(第 3 章 思考题 9 语境+3.3.3.1): 原书明确指出失败模式——Reviewer 与 Proposer 同模型且只看 Proposer 挑选的片段时,系统会合入同源错误与证据覆盖不足的错误;改进方向即模型独立性、证据覆盖(可查完整知识库与原始证据)、工具权限(Proposer 不能碰主分支)三方面。另: OpenViking(3.3.2)用 Markdown+Git 组织知识,Agent 在工作分支写知识、审核后合入,文件间必须建链接与索引页——"不同模型主动建立链接的意愿不同,写入提示词必须写明确"。

## A2 — 触发场景

- 知识库/用户记忆上线后要定"谁能写、怎么写、怎么防写坏"
- 多次更新后出现重复条目、新旧说法并存、摘要偏离原文
- 多租户/多权限等级下的知识可见性设计
- 语言信号: "知识库更新", "写入审核", "知识冲突", "定期整理", "知识投毒", "租户隔离", "过期内容"
- 区分: 检索管道本身见 rag-pipeline;单用户个性化记忆的格式选型见 user-memory-system(治理原则同源);Agent 自我进化中的同类 PR 协议见 continual-evolution(本卡管陈述性知识)

## E — 执行步骤

1. 建三层结构: 原始证据层(对话/轨迹/文档,append-only,进 Git)、知识层(Markdown/代码,可修订)、服务层(向量索引等派生物,可随时从已合入版本重建)。完成标准: 线上每条知识能回答"从哪条证据来、谁在何时批准"。
2. 增量更新流水线: 事件触发→Proposer 在工作分支提最小 diff(先检索相关已有条目,带证据引用与时间)→异源 Reviewer 对照原始证据审核→拒给可执行意见→迭代至批准(设最大迭代数/成本预算,超限转人工,不默认放行)→CI(格式/链接/元数据/权限标签;代码化知识加类型检查与测试)→从合入版本增量重建受影响索引。
3. 权限与模型分工: Proposer 只能写工作分支;Reviewer 只读证据、提交审核结果;只有合并流程可动主分支;两 Agent 来自不同模型家族且能力相近;均可按需查询被授权范围内的完整知识库与原始证据库。
4. 定期整理(按时间或阈值触发——新增量/冲突数/检索质量下降): 全量扫描去重合并→逐段回原始数据核查旧摘要(分批处理须保留覆盖清单)→冲突追溯各自来源,分时间/对象/条件都成立则把适用场景写入知识而非删除;产物同样走分支+异源审核;整理后回放典型检索用例确认旧知识仍可找到。
5. 失效与权限: 每个分块带版本号与生效/失效时间,检索期过滤已失效内容或显式标注废止;检索按调用者权限过滤,租户间索引与元数据隔离。
6. 验证: 注入一次故意错误提交,确认 Reviewer 能拦;审计链抽查——随机取 N 条线上知识反查证据。

输入契约: 知识来源与更新频率、权限模型(部门/租户/角色)、可用的异源模型对。输出契约: 更新流程规范+整理周期与触发阈值+审计记录格式。

## B — 边界

- 全量重组的 diff 大,按目录/主题拆多个 PR 但共享同一整理计划与覆盖清单
- 同源互审不构成独立性——不同家族的偏好差异才是降低同类错误的来源;能力悬殊的配对(弱审强)也不可靠
- 冲突不得强行收敛: 证据不足时保留冲突与待确认状态,不猜
- "检索层权限过滤"必须在内容进入 LLM 上下文之前——进了上下文就难以保证不泄露到回答
- 云端 LLM 做日志脱敏违背隐私初衷(敏感内容已出域),脱敏应在本地
