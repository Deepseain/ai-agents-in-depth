# 评估驱动的系统改进与内部评估基础设施

## R — 原文

> "看到 Agent 表现下降时,应先检查评测系统本身,再动 Agent……这些问题在结果数字上都跟模型退化一模一样,只有审查完整的轨迹才能区分。" —— 第 7 章 7.9

> "一轮证据只支持与它规模相称的下一步……好的 Benchmark 报告不只给出一个分数,还应写清结论适用于哪里、哪些底线没有通过、下一轮要验证什么。" —— 第 7 章 7.9.4

## I — 阐释

从分数到改进的科学闭环: 观察→假设→实验→验证→新认识。读报告的纪律: 先看失败集中在哪些任务/能力(失败簇),再回放轨迹分清问题出在"看、想、做、验"哪一环——只盯总分会让小而集中的失败簇被忽略。实验纪律: 每轮只改一个变量(固定模型/参数/种子/步数/环境,交替运行顺序),上一轮暴露的问题恰是下一轮唯一要验证的改动;先试最便宜的改法(加提示),无效再查"Agent 到底看见了什么"(输入通道)——提示补不回根本没看见的信息。部署纪律: 子集通过只获得完整复测资格,不等于可以部署;报告写清结论适用范围与未过的底线。内部评估基础设施五件套(把 ML 实验方法嵌入产品工程): 消融开关(每个主要特性可独立关闭,启动路径早期注入,定期跑以发现"特性债务")、AB 测试(多臂设计看剂量效应;区分机制指标——你直接改的东西,与目标指标——你真正关心的;设护栏指标——不能变差的底线;记录基线统计)、双层特性开关(编译时物理移除+运行时服务端下发)、提示词敏感性管理(系统提示确定性渲染+版本快照+每次变更跑回归,当代码对待)、隐私感知分析(类型系统强制"已验证非敏感"才可采集——采集不安全就无法评估)。

## A1 — 书中案例

worked_example(第 7 章 7.9 表 7-5): AndroidWorld 4 项 Wi-Fi 任务失败簇。H1 加导航提示: 25%→25%,token 0.47×——证明问题不在提示词;H5 把不兼容的 accessibility feed 换成 UIAutomator 元素树: 25%→100%,token 2.498×——"看不见"解决但太贵;H5C 删掉不可见/无文字/不可操作的容器节点: 100%→100%,token 0.506×——保成功率砍噪声。全程不换模型,只改 Harness 如何表示界面,先后解决"能不能做成"与"做成是否划算"。子集 4/4 后的下一步是 116 任务×5 种子的完整复测+token/延迟门槛,而非宣布 100%。

## A2 — 触发场景

- 手里有 benchmark/评估报告,要决定"下一步改什么"
- 团队要建持续改进机制: 特性有没有用、AB 怎么做、提示词怎么管版本
- 改进后分数反降,或新改动"感觉有用"没证据
- 语言信号: "改进闭环", "消融实验", "ablation", "AB 测试", "feature flag", "提示词版本管理", "单变量实验"
- 区分: 评估构造见 eval-fundamentals,打分与归因见 llm-judge-failure-attribution,选模型见 model-selection-cost;本卡管"分数→改动→验证"的迭代纪律与内部基础设施

## E — 执行步骤

1. 诊断前先查评测系统: 结果下降时先排除环境资源不足、验证器 bug、用例与生产脱节——审查完整轨迹再动 Agent。完成标准: 下降原因定位到评测侧或 Agent 侧有轨迹证据。
2. 找失败簇: 按任务与能力标签交叉统计,找集中失败区域;回放代表性轨迹,把失败归类到看(输入缺失)/想(决策错)/做(执行错)/验(验证缺)。完成标准: 失败簇对应到一类能力缺陷。
3. 构建假设并排序: 从最便宜改法开始(提示/规则),无效再动结构(输入通道/工具/上下文表示);每个假设写明预期提升与验证方法。
4. 单变量实验: 每轮只改一个变量,控制其余(模型/任务参数/种子/步数/环境,交替运行顺序);记录成功率+token+延迟+是否回退。完成标准: 因果可归因到该轮唯一改动。
5. 数据驱动权衡: 按"结论适用于哪里/哪些底线没过/下一轮验证什么"写报告;子集通过→完整复测(扩任务集、多种子、设 token 与延迟门槛)→才谈部署;高成本改进限定关键场景。
6. 建内部基础设施(生产系统): 消融总开关+每特性独立开关;AB 多臂设计并区分机制/目标/护栏指标;特性开关双层(编译时移除+运行时下发,曝光事件每会话至多记一次);提示词确定性渲染+git 版本快照+变更跑评估回归;分析接口用类型系统强制隐私约束。
7. 验证: 对每个"有用"的特性跑一次消融,确认去掉后指标确实下降——发现特性债务即清理。

输入契约: 评估报告与原始轨迹、可改动的 Harness 组件清单、部署门槛(成功率/成本/延迟)。输出契约: 改进路线图(假设列表按成本排序)+单变量实验记录+复测报告+基础设施配置。

## B — 边界

- 同时堆多个改动=无法归因——"一轮只改一个"是硬纪律,不是风格偏好
- 输入不是越多越好: H5 的教训是信息够了但噪声贵;裁剪规则要自动可重复
- 机制指标改善≠目标改善: 缩短计划文件可能反而增加编辑循环——永远问"我改的和我在乎的是同一个吗"
- 消融开关必须极早期注入(在任何模块级常量捕获配置之前),事后加装无效
- 子集/小样本结论不得写成系统整体结论——报告里的适用范围声明不可省
