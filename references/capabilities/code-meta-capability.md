# 代码作为元能力的六维应用

## R — 原文

> "元能力是一种'能创造其他能力'的能力:Agent 用它当场写出新工具、新约束、新表达形式来完成任务,而不必事先把所有能力都预制好。" —— 第 5 章 5.2

> "更好的方案是 Artifact 模式……数据从数据库直达用户界面,完全绕过了 LLM 这个'中间人'——LLM 只负责写查询语句。" —— 第 5 章 5.2.5

## I — 阐释

代码不只是写程序,是 Agent 形式化思考与精确表达的语言,按作用对象分六个方向: ①思考工具——LLM 出理解、代码解释器出精确计算(符号计算/约束求解),脚手架厚度随模型能力此消彼长;②业务规则约束——自然语言规则供解释沟通,关键决策点用代码校验守门,价值在防不可逆错误而非省 token;③多媒体生成——PPT/视频本质是 OOXML/API/代码,配提议者-审核者渲染迭代(Reviewer 看截图,引入生成时不存在的视觉信息);④系统适配器——无 SDK/格式漂移的接口当场生成胶水代码,日志解析失败自动反馈再生成的自适应闭环;⑤生成式 UI——动态表单澄清意图(级联逻辑一次填完)、A2UI 声明式协议(只出 JSON 清单、客户端安全组件渲染,防任意代码执行)、Artifact 模式(LLM 生成 SQL/可视化代码交系统执行,不经手数据)、动态生成软件须把信任边界下移到数据层(行级安全/受控视图,应用层代码随时被改写时唯一可靠的是数据库层);⑥Agent 自举——复制高质量范例+适应性修改(而非从零生成),OpenClaw doctor 式"确定性检查打底+LLM 兜底长尾"。

## A1 — 书中案例

worked_example(第 5 章 5.2.1): "40 名学生 60% 选数学、45% 选物理、25% 都选,只选物理的有多少人"——纯自然语言推理常误从数学人数中减(答 14,错);写成 `both = int(40*0.25); only_phys = phys - both` 得 8。实验 5-4: 弱模型+约束求解器在 K&K 逻辑谜题达 90%+,强模型纯思考即解、增益归零——脚手架该多厚取决于模型能力边界。worked_example(5.2.3): 法兰盘(五六个参数完整定义)代码路线可程序化验证、改 M5→M6 只改一个数字;绿植(内在复杂度近乎无限)生成模型路线自然生动——按"紧凑精确描述+精度要求"选路。

## A2 — 触发场景

- Agent 要做数学/逻辑/统计类精确任务,老老实实用自然语言算
- 要把模糊业务政策变成不可绕过的约束;文档/PPT/视频生成
- LLM 需要处理大量数据(查询/汇总/可视化)——决定"模型读数据"还是"模型写代码、系统执行"
- 对接无 SDK/格式常变的系统;让 Agent 生成界面或创建新 Agent
- 语言信号: "code interpreter", "用代码思考", "业务规则代码化", "生成式 UI", "SQL 生成", "agent 自举", "代码 vs 生成模型"
- 区分: 工具执行安全见 execution-tool-safety(本卡的生成代码都要过那套栈);Artifact 的"生成-执行分离"与提议者-审核者的完整协作设计见 multi-agent-architecture

## E — 执行步骤

1. 判断该不该用代码: 精确性要求高(计算/规则/可验证结构)、数据量大(该走 Artifact 绕过 LLM)、产物有紧凑精确描述(文档/UI/工业件)→用代码;内在复杂度近乎无限且无精度硬约束(自然图像/艺术)→生成模型;两者可混用(几何代码化+纹理生成)。完成标准: 每个产物有"代码/生成模型/混合"的归属判定及一条判据引用。
2. 思考工具化: 遇数学/逻辑题,形式化为代码(符号计算库/约束求解器)在沙盒执行取精确结果;按当前模型能力决定投入——模型已稳的部分不套脚手架。完成标准: 精确结果来自代码执行而非模型口算,且在目标模型上验证过增益非零才保留脚手架。
3. 规则约束化: 政策/流程中不可逆的判定写成校验代码置于操作前(参数设计引导模型先核对,服务端真值裁决,见 execution-tool-safety);可解释部分留自然语言。
4. 内容生成: 结构化产物(PPT/报告/图表)生成代码→渲染→独立 Reviewer 看渲染结果给结构化改进建议(页码/问题/严重度)→迭代至达标或到最大轮数(两类显式终止: 质量达标/预算上限)。
5. Artifact 模式: 数据类任务让 Agent 生成 SQL/前端代码作为独立产物交系统执行——执行层用只读账号、仅允许白名单 SELECT、参数化绑定、限制行数时长、可视化代码沙盒运行;LLM 不读原始数据行。完成标准: 数据行从不经过 LLM 上下文,执行层注入测试(DDL/多语句/越权)被拒。
6. 界面生成: 标准交互用声明式协议(JSON 描述+客户端安全组件渲染);确需直接生成 HTML 时按 XSS 级风险对待(沙盒/ CSP);动态生成的应用层代码的权限判断不作为最终防线——信任边界下移到数据层。完成标准: 组件清单全部来自受信任目录;越权数据访问在数据层被拒(应用层漏写也不放行)。
7. 验证: 代码路线的产物做程序化验证(跑测试/量尺寸/对照规格);Artifact 检查执行层拦截(DDL/多语句被拒);生成 UI 检查组件白名单。

输入契约: 任务类型、可用沙盒与执行环境、精度/可验证性要求。输出契约: 按方向产出(可执行代码/校验器/artifact/界面描述)+程序化验证结果。

## B — 边界

- 代码执行是攻击面: 沙盒(默认断网/限额/凭证不挂载)不可省;A2UI 声明式协议的本质是"只能点菜单上的菜,不能进厨房"
- 蒸馏/内化风险: 部分给模型短板打补丁的代码路径会被下一代模型吃掉(文生图提示词改写已发生)——投入前问"这是能力缺口还是接口缺口"
- 自举防退化: 从零生成 Agent 常见缺陷(上下文随意/工具描述简略/技术选型过时),基于范例修改优于从零写
- Artifact 不替代权限检查: SQL artifact 仍需只读账号与语句白名单
- 作者对"代码为中心"的适用边界自陈: 开放任务型通用 Agent 成立;任务空间封闭的垂直 Agent 中代码只是工具箱一员
