# 多 Agent 架构决策:信息增量与共享×拓扑

## R — 原文

> "核心判据只有一条:协作过程是否引入了单个 Agent 在生成时无法获得的新信息?" —— 第 10 章 10.2

> "好的协作不是暴露彼此的思考过程,而是约定清晰的接口、边界、权限和验收标准。" —— 第 10 章 10.7

## I — 阐释

是否用多 Agent,先过信息增量判据: 同模型自审(无新信息,通常无效)、多 Agent 辩论同段文本(等计算量下不优于单 Agent——数据处理不等式)、审核者读执行结果/渲染截图/外部工具验证(有新信息,显著提升)。工程有效的"多 Agent"几乎都含外部反馈环。确定要用后,两个架构维度: ①上下文共享与否——共享(后续 Agent 继承完整轨迹,信息不丢但膨胀+角色惯性)适合流水线式交接;不共享(各 Agent 独立上下文)利于并发/模块化/权限,靠三种通信机制传"移交包"(任务描述+已确认事实+产物引用,文件路径而非内容)。角色切换用 Skill(知识/流程/风格差异,前缀稳定)还是 transfer_to_agent(权限/工具隔离/硬约束差异,可 schema 级隐藏工具)。②拓扑——对等(2-3 个平等 Agent 迭代互审,提议者-审核者最小不变量: 审核者必须读独立证据、退回给可定位的修复条件、不可修改测试与发布门槛)、管理者(Manager 把子 Agent 当工具调用;强模型给规划者——弱规划者是系统瓶颈;并行时定义"第一个已验证成功"的幂等结算点)、去中心化(handoff 移交,带 visited/budget 防成环)。文件系统按四区域布局(私有 scratchpad/共享空间/外部挂载/系统内置只读),控制平面四原语(结构化消息信封/状态查询走进度文件/优雅终止+级联取消/资源调度与预算)。

## A1 — 书中案例

worked_example(第 10 章 实验 10-2): 书籍翻译——单 Agent 随章节累积上下文会"迷失"术语约定(第九章与第二章译法不一)。管理者模式四 Agent: Glossary(全书提术语表,写共享空间后销毁)、Translation(每章独立上下文,只见本章+术语表+指南)、Proofreading(全文只做一致性检查)、Manager(只存任务描述/计划/调用记录/文件索引,不存译文)。对照证明: 上下文隔离使每个 Agent 在精简专注的上下文中工作,效率高错误少。reported_case(10.2): Anthropic 45 个 Agent 共享论坛协调漏洞挖掘——266 个漏洞(2700 万 token),独立 Agent 并行方案仅 21 个(650 万 token): 开放搜索空间里通信能动态转移搜索重点、形成分工。

## A2 — 触发场景

- 纠结"这个任务要不要拆成多个 Agent"、"加个审查 Agent 有没有用"
- 设计多 Agent 系统: 共享记忆还是隔离?谁调度?怎么传上下文?
- 多 Agent 系统 token 成本一个数量级高于单 Agent,要判断值不值
- 语言信号: "多 agent", "multi-agent", "协作架构", "propose-review", "manager agent", "上下文共享", "handoff"
- 区分: 失败模式与防御见 multi-agent-failure-modes(本卡管"怎么设计",那张管"怎么防崩");异步事件处理是单 Agent 内的时机问题见 async-event-agent;子 Agent 隔离做压缩的手段见 context-compression

## E — 执行步骤

1. 过信息增量判据: 列出协作中每个 Agent 为其他 Agent 提供什么新信息(执行结果/渲染截图/外部验证/独立视角的数据源)。判停: 全部是"再看一遍同样的文本"→单 Agent 或改为生成-验证分工(验证用外部工具);有新信息→继续。完成标准: 判据结论可追溯到具体的新信息条目,而非"多一个更稳"。
2. 定共享维度: 流水线式角色交接(需求→开发→审查,后者要前者完整上下文)→共享轨迹;并发/异构/权限隔离需求→不共享,定义移交包格式(任务+验收标准/已确认事实与约束/产物文件引用),传路径不传内容。完成标准: 每对协作 Agent 的共享决策有理由;移交包三要素齐备。
3. 选拓扑: 双角色互审迭代(写-审/生成-验证)→对等+提议者-审核者;子任务多、有依赖、需动态调度→管理者(最强模型与最精心提示词给 Manager;子 Agent 返回结构化摘要而非全量轨迹;并行时设幂等结算点,一个验证成功即广播取消其余);无中心控制诉求/单点故障敏感→去中心化 handoff(带访问链与预算上限防环)。完成标准: 拓扑选择对应任务结构特征;Manager 位配置了最强模型。
4. 角色切换机制: 权限/工具可见性/合规边界差异→独立 Agent 或 transfer_to_agent(Harness 代码限权);仅知识/流程/风格差异→Skill 加载(前缀稳定,缓存友好)。
5. 搭数据与控制平面: 文件四区域(私有工作区/共享空间/外部只读挂载/内置只读资源);消息带信封(发送者/目标/类型/JSON 负载);状态查询约定 progress.md(轻量、可检测停滞: 超时无更新即判卡住);终止沿创建关系级联取消(优雅终止优先,超时强杀);启动子 Agent 时设 token/步数预算。
6. 验证: 移交包完整性测试(接收方无需追问即可开工);并发冲突注入(见 multi-agent-failure-modes);成本核算——多 Agent 收益须覆盖数倍 token 开销。

输入契约: 任务结构(可分解性/子任务依赖)、各角色的权限差异、可用的差异化模型与信息源、预算上限。输出契约: 架构决策记录(判据结论+共享维度+拓扑+通信协议)+移交包格式+预算与终止规则。

## B — 边界

- 辩论模式的效果有争议: 等计算量下与单 Agent 持平——学术论文中的多 Agent 收益很可能来自更多总计算量
- "多个实例"≠"多种思路": 模型/上下文/脚手架高度相似时局部错误变系统性故障(需主动差异化)
- 管理者的单点瓶颈: Planner 弱则全盘皆输(WebArena-Lite 54% 的核心贡献是改善规划而非执行);Manager 上下文随调用膨胀需只存索引
- 共享上下文的角色惯性: 审查者继承写作者的思维框架会偏离本职——检测与消除是开放问题
- 步骤预算要显式管理: 单纯加步骤不能保证提升(Agent 浅层搜索后"饱和"),需预算感知机制
